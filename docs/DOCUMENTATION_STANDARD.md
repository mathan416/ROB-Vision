# Documentation standard

This is an editorial checklist for future R.O.B. Vision guides. It is a contributor document, not a player guide.

## Player Help and game manual

- Put the player's task first: start, pair, play, read a status, or fix a problem. Name the page or device where each action happens, use the visible control label, and state the result to expect.
- Explain the virtual model once near the introduction. Do not repeat that a physical robot or accessory is absent throughout Help and the manuals.
- Show game controls and piece behavior near the relevant task. Distinguish what the game sends, what the virtual model shows, and what the game screen alone can confirm.
- Keep Buddy's fiction in an optional, clearly titled story section. Tell the story as a story. Do not interrupt setup or troubleshooting with character-development notes, legal caveats, or release history.
- Open each player guide with the reader's goal and the result they can expect. Keep implementation status, unverified behavior, acceptance criteria, and test-machine narration in the technical reference or dated verification reports.
- Give essential information as text as well as imagery or color. Screenshots should clarify a specific control or state and have descriptive alternative text.

## User guide and quick reference

- Start with a brief product description, supported equipment, and the path to a working first session. Use short, numbered procedures for installation, pairing, Test mode, and play.
- Keep the quick reference to controls, signals, and recovery actions. Link to fuller explanations rather than repeating them.
- Describe current behavior. Move dated validation detail, design decisions, and experimental paths to engineering reports.

## Technical reference

- State interfaces, data flow, supported versions, defaults, failure behavior, and security boundaries precisely. Separate verified behavior from remaining limits.
- Keep configuration values and command names searchable. Link to test reports for evidence; do not turn the reference into a development diary.
- Keep attribution and rights information in the repository's rights and release material, away from operational steps.

These rules apply the distinction between how-to, reference, and explanation in [Diátaxis](https://diataxis.fr/start-here/); [Microsoft's procedure guidance](https://learn.microsoft.com/en-us/style-guide/procedures-instructions/writing-step-by-step-instructions) and [Google's procedure guidance](https://developers.google.com/style/procedures) for task steps; [Google's image guidance](https://developers.google.com/style/images) for purposeful screenshots and alt text; and [Xbox Accessibility Guideline 106](https://learn.microsoft.com/en-us/xbox/accessibility/xbox-accessibility-guidelines/106) for making controls and game information available beyond visuals alone.
